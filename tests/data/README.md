# Test fixtures — cross-validation of indicators, metrics and the wallet

Four independent cross-checks, all fully offline, all able to skip when their
reference library isn't installed:

| Suite | Layer | Reference |
|---|---|---|
| `tests/talib_validation.rs` | indicators | [TA-Lib](https://ta-lib.org/) |
| `tests/metrics_validation.rs` | equity-curve metrics | [empyrical](https://github.com/quantopian/empyrical) |
| `tests/wallet_validation.rs` | `PaperWallet` execution | [vectorbt](https://github.com/polakowo/vectorbt) |
| `tests/trade_metrics_validation.rs` | trade-level metrics | [backtesting.py](https://kernc.github.io/backtesting.py/) |

Plus one guard that is **not** skippable and needs no reference library:
`tests/metrics_coverage.rs` walks `metrics::flatten` and fails if any field has
neither a reference value in a committed fixture nor a written exemption. Adding
a metric and forgetting to give it a reference is a red build, not a silence.

## Files

- `aapl_monthly.csv` — committed OHLCV input for the TA-Lib check
  (`date,open,high,low,close,volume`). A fixed monthly snapshot used purely
  as a shared input; the cross-check is valid because fugazi **and** TA-Lib
  consume this exact file. Replace it with your own export (same columns) for
  authoritative AAPL data if you like.
- `talib_expected.csv` — generated by `tools/gen_talib_fixtures.py`, and
  **committed**, so the cross-check runs on every checkout. One column of TA-Lib
  output per indicator, aligned row-for-row with the input. Regenerate and
  re-commit it whenever you add an indicator to the generator.
- `metrics_returns.csv` — committed 252-bar per-bar returns series for the
  metrics check, produced by a fixed-seed numpy draw (see
  `tools/gen_metrics_returns.py`). Rerun only when the fixture needs to be
  replaced; commit the regenerated file alongside its updated
  `metrics_expected.csv`.
- `metrics_expected.csv` — generated by `tools/gen_metrics_fixtures.py`, but
  **committed** (unlike its TA-Lib counterpart), so the metrics cross-check runs
  everywhere. One row per `(metric, expected)` reference value computed by
  empyrical (plus a few manual numpy formulas for fields empyrical doesn't
  cover). Regenerate and re-commit it whenever `metrics_returns.csv` or the
  generator's constants change.
- `wallet_bars.csv` — committed input for the wallet check: a 60-bar OHLCV
  series **and** the order schedule replayed over it (`target` = the position,
  in units, submitted at that bar's close, filled at the next bar's open). One
  file rather than two because the schedule is only meaningful against these
  exact bars. Produced by `tools/gen_wallet_bars.py`; the schedule inside it is
  hand-written to walk entry / add / partial reduce / exit / short / reversal
  rather than drawn.
- `wallet_expected.csv` — generated by `tools/gen_wallet_fixtures.py`, and
  **committed**. Per-bar `cash`/`position`/`equity` under each of five cost
  configurations (`zero`, `commission`, `spread`, `slippage`, `full`), from
  `vectorbt.Portfolio.from_orders`.
- `trade_metrics_fills.csv` — committed input for the trade-metrics check, and
  unusually it is itself *generated*: it holds the fill blotter and equity curve
  backtesting.py produced, which fugazi is then fed. Feeding the reference's own
  fills back in is what makes the comparison about the statistics rather than
  about which trades happened.
- `trade_metrics_expected.csv` — generated by
  `tools/gen_trade_metrics_fixtures.py`, and **committed**. One
  `(metric, expected)` row per `trades.*` and `drawdown.*` reference figure.

## Regenerating the reference values

None of the four reference libraries is a Rust dependency; they're external
tools used once to produce the fixtures. [`pixi.toml`](../../pixi.toml) at the
repo root defines the environment — conda-forge for the TA-Lib C library, its
Python wrapper, empyrical and vectorbt, plus PyPI for backtesting.py, which
conda-forge doesn't ship:

```sh
pixi run gen-talib     # tests/data/talib_expected.csv
pixi run gen-metrics   # tests/data/metrics_expected.csv
pixi run gen-wallet    # tests/data/wallet_expected.csv
pixi run gen-trades    # tests/data/trade_metrics_{fills,expected}.csv
pixi run gen           # all four

cargo test --test talib_validation --test metrics_validation \
           --test wallet_validation --test trade_metrics_validation
```

`pixi` needs no `activate` step and creates the env on first `run`. Nothing
else in the repo depends on it: the crate builds with `cargo` alone, and the
bindings' dev venv is separate (`scripts/ci-local.sh` builds it with `uv`).

(Or with pip, if the TA-Lib C library is already installed: `pip install TA-Lib
numpy`, then `python3 tools/gen_talib_fixtures.py`. See the warning below.)

### Why the environment is pinned

`pixi.lock` is committed, and that is the point of using pixi at all. These
CSVs are *reference values* — `metrics_validation.rs` compares against them to
1e-9 — so the environment that produces them is part of the reference. Its
predecessor (`tools/environment.yml`, now removed) named four packages with no
version bounds, which cost real correctness in two ways:

- **It stopped working.** empyrical has been unmaintained since 2020 and
  `downside_risk` still calls `np.NINF`, removed in NumPy 2.0. Solving those
  four unpinned names today picks numpy 2.5 and `gen_metrics_fixtures.py` dies
  with `AttributeError` partway through. `pixi.toml` holds `numpy = "<2"` for
  this reason, with the rationale in a comment there.
- **It made fixture diffs unreadable.** Regenerating under the pinned env moved
  three stddev-derived values (`annualized_volatility_pct`, `sharpe`, `sortino`)
  in their last 1–2 ULP — an OpenBLAS kernel difference, ~7e-15 relative, well
  inside the 1e-9 tolerance. Benign, but indistinguishable at a glance from a
  real regression. With the env pinned, regenerating without changing anything
  produces an **empty** `git diff`, so anything that does show up is yours.

So: after regenerating, read `git diff tests/data/`. The pip path above is
unpinned and gives up this property.

## The skip is opt-out

The test **skips** (printing these steps) when `talib_expected.csv` is absent
*or* stale — i.e. missing a column for a newly added indicator — so `cargo test`
stays green for contributors who don't have TA-Lib. Regenerate the fixture after
adding any indicator to the generator.

That default is convenient and a poor guarantee: **a skip is indistinguishable
from a pass**, so a cross-check can rot for months without a red build. That is
exactly what happened here — `talib_expected.csv` was listed in `.gitignore`, so
it was absent from every clean checkout and the drift guard `CONTRIBUTING.md`
advertises compared precisely nothing. Both fixtures are now committed, and CI
runs with the switch below on, so the failure mode cannot recur silently.

Set `FUGAZI_REQUIRE_FIXTURES=1` to turn every missing-or-stale fixture from a
skip into a failure:

```sh
FUGAZI_REQUIRE_FIXTURES=1 cargo test --test talib_validation --test metrics_validation \
                                     --test wallet_validation --test trade_metrics_validation
```

**CI runs the Rust test job with this set** (see `.github/workflows/ci.yml`), so
a re-ignored or stale fixture fails the build. It is also the way to prove
locally that a suite really compared rather than returning early.
The suites also assert they compared a non-zero number of cells, so a
present-but-empty fixture fails rather than passing vacuously.

`tests/metrics_coverage.rs` closes the remaining hole: the switch above catches
a fixture that went missing, but not a *metric* that was never added to one.
That guard reads the fixtures for their key sets only, so it never skips —
every field of `metrics::Metrics` must carry a reference value or a written
exemption saying which suite covers it and why no reference library does.

Meanwhile `tests/indicator_reference.rs` holds the numeric line
unconditionally — its expected values are hand-derived from each indicator's
definition, so it needs no external library and cannot skip. Neither file
replaces the other: this one pins fugazi against *its own* documented formulas,
the cross-checks pin it against an independent implementation's conventions.

## What is compared, and tolerances

### Metrics (`metrics_validation.rs` vs empyrical)

The generator produces 28 reference values covering `run.*`, `returns.*`,
`risk_adjusted.*` and `drawdown.*`. Each is checked to `1e-9` absolute (or
`1e-9` relative for large magnitudes) — an exact float agreement, since
fugazi and empyrical implement the same formulas over the same input. The
alignment relies on fugazi using sample stddev (Bessel-corrected, `ddof=1`)
for `stddev_bar`/annualized volatility and an `n`-divisor downside stddev
with `rf_per_bar` as the MAR threshold — the conventions empyrical uses.
Omega uses arithmetic per-bar rf as its threshold in both codebases (the
generator reproduces this rather than calling `empyrical.omega_ratio`, which
uses a geometric per-bar conversion). Trade-level metrics aren't part of this
cross-check — the generator hands `from_report` a synthetic report with no
fills, because empyrical takes a returns series and has no notion of a trade.
They are covered by `trade_metrics_validation.rs` instead.

### The wallet (`wallet_validation.rs` vs vectorbt)

Per-bar `cash`/`position`/`equity` to `1e-9`, over five cost configurations.
The load-bearing thing it pins is **fill timing**: fugazi queues a market order
at bar N and fills it at bar N+1's open, and the generator expresses that by
placing vectorbt's order one row later, priced at that row's open. A wallet that
started filling at the signal bar's close — the classic lookahead — moves every
figure downstream and turns this suite red.

Costs are checked one leg at a time (`commission`, `spread`, `slippage`) so a
mismatch names the leg. The `full` configuration deliberately omits spread:
fugazi composes the two price legs multiplicatively, vectorbt has one
adverse-price knob, and folding both into it gives `a + b + ab` on a buy against
`a + b − ab` on a sell — one fraction can match one side, never both. That
composition stays with the unit tests in `src/costs/mod.rs`.
`tools/gen_wallet_fixtures.py` carries the derivation.

Out of scope, because vectorbt shares none of the semantics: stops,
take-profits, resting limits and their intrabar ordering, fractional
shrink-to-fit sizing, portfolio netting.

### Trade metrics (`trade_metrics_validation.rs` vs backtesting.py)

27 reference values across `trades.*` and the `drawdown.*` duration/count/depth
fields, to `1e-9`. The generator emits the **input** as well as the expected
values: fugazi is fed the fill blotter and equity curve backtesting.py itself
produced, so a divergence is always a disagreement about the statistics rather
than about which trades happened.

Scope is non-overlapping round trips only (flat → position → flat). fugazi
reconstructs trades at volume-weighted average cost, backtesting.py splits per
entry order FIFO; the two coincide exactly on round trips and genuinely differ
on adds, partial closes and reversals, so those stay with the unit tests. The
generator refuses to run on an overlapping schedule. Commission is zero and must
stay so — backtesting.py reports trade PnL net of commission, fugazi computes it
from fill prices and books commission separately.

Five of backtesting.py's headline statistics answer a *different question* from
the fugazi field sharing their name. Each is documented in the generator and
checked against the value fugazi's definition implies:

| backtesting.py | Difference from fugazi |
|---|---|
| `Profit Factor` | sums trade **ReturnPct**; fugazi sums trade **PnL** |
| `Avg. Trade [%]` | **geometric** mean of `1 + ReturnPct`; fugazi is arithmetic |
| `Exposure Time [%]` | counts entry *and* exit bar as held (`x − e + 1`); fugazi counts `x − e` |
| `Avg. Trade Duration` | rounds to whole days via `Timedelta`; fugazi keeps the fraction |
| `Max. Drawdown Duration` | includes the recovery bar; fugazi counts only bars below the peak |

`Win Rate [%]`, `Kelly Criterion`, `# Trades`, `Max. Trade Duration`,
`Avg. Drawdown [%]` and `Equity Final [$]` are taken straight from
backtesting.py with no reinterpretation, and agree to `1e-9`. Those are the
stronger evidence.

### Indicators (`talib_validation.rs` vs TA-Lib)

Indicators whose conventions match TA-Lib exactly are checked to `1e-6` over
every warmed-up bar: **SMA, RSI, STDDEV, BBANDS (upper/mid/lower), MAX, MIN**
(MAX/MIN of high/low are the Donchian channel), **TRANGE**, the fast stochastic
**%K** (`STOCHF`, fed `close` as high/low/close so it positions the close within
its own rolling range, matching fugazi's `Stochastic` scaled to `[0, 100]`), and
the volume indicators **OBV, AD** (Chaikin A/D line) and **MFI** — cumulative or
windowed sums with no recursive seed. (**VWAP** has no TA-Lib function, so it is
covered by unit tests only, not this cross-check.)

**EMA**, **ATR**, **MACD** (line/signal/histogram) and **ADX** (with +DI/-DI)
differ only in *seeding*: fugazi seeds each recurrence from the first sample(s),
while TA-Lib uses a different seed (an SMA for EMA-family, summed Wilder state
for ADX-family). That difference decays geometrically, so these are checked with
a looser tolerance over the tail of the series only.

Indicator parameters live in both `tools/gen_talib_fixtures.py` and
`tests/talib_validation.rs` — keep them in sync. Same rule for the metrics
constants (`INITIAL_CASH`, `BARS_PER_YEAR`, `RISK_FREE_RATE`) which live in
both `tools/gen_metrics_fixtures.py` and `tests/metrics_validation.rs`.
